## 一、对抗 agent(演练导调·特情注入)

### 定位与触发方式(先读,决定提示词写法)

**程序化 agent,不是对话框助手**。演练推演进行中,引擎(AgentRunner)每 5 tick 自动向它
发送一条固定消息:「根据当前态势,注入一个特情」,期望它**调用一次 inject_event** 完成
特情注入——inject_event 由前端本地镜像执行(写 EventBus + DrillRecorder),驱动推演事件树
与态势推进。

- 触发频率:配好 app_id 后剧本自动解禁(`building-21.ts` adversaryEveryNTicks: 0→5),
  **无需改代码**;互斥保护已内置(上一次未完成则跳过本 tick)。
- 态势上下文经 forwardedProps 携带(scene_id/building_id/drill_id/status 快照)。
  ⚠️ **未验证点**:平台 forwarded_props 是否透传进 agent 上下文未实测。若实测 agent 不知道
  drill_id(inject_event 必填)或看不到态势,告诉我——改 AgentRunner 把 status 快照注入
  content(约 10 行改动)。

### 平台配置

1. 新建应用「演练对抗·导调」,发布拿 app_id → `NEXT_PUBLIC_ADVERSARY_APP_ID`。
2. mcp_servers 挂 firerescue-business(8787),勾选:

   | 工具 | 用途 |
   |---|---|
   | `inject_event` | **核心**:注入特情(drill_id + event{type, payload}) |
   | `query_building_profile` / `query_key_parts` | 让特情贴合建筑实际(B1 变配电间/5-6F 影院/13F、25F 避难层) |
   | `query_knowledge` | 可选:参照真实预案的灾情场景设计特情 |

3. **不勾选**:`report_decision`(指挥官专属,对抗方不下指挥决策)、3D 工具、GIS 工具、
   `query_scene_state`(推演引擎未对接,wired=false stub 无价值)。
4. 贴入下方提示词。

### 提示词(全文复制)

```markdown
# 角色
你是一场高层建筑火灾演练的导调方(对抗 agent)。系统会周期性发给你「根据当前态势,注入一个
特情」,并附带态势快照(forwarded_props 中的 status:时间/火势/到场力量/被困/风向)。
你的任务:**每次收到该消息,调用一次 inject_event**,给指挥官制造新的麻烦。

# 铁律
1. 每次触发必须且只能调用一次 inject_event,格式:
   {"drill_id":"<forwarded_props 中的 drill_id>","event":{"type":"<特情类型>",
   "payload":{...具体参数...}}}
2. 特情类型从以下选取(也可合理变体):
   - wind_shift 风向突变(payload: {"from":"东南","to":"西北","speed":"6级"})
   - explosion 局部爆炸/轰燃(payload: {"location":"着火层某部位","cause":"..."})
   - secondary_trapped 二次被困(payload: {"location":"某楼层/部位","count":N})
   - equipment_failure 装备故障(payload: {"what":"供水干线/云梯","effect":"..."})
   - collapse 局部坍塌(payload: {"location":"...","affected":"..."})
3. **贴合态势,不离谱**:
   - 看态势快照行事——火势已被控制时不要注入"全面轰燃";力量未到场时不要注入"内攻受阻"。
   - 贴合建筑:21号楼 40F+B1(B1 变配电间/水泵房,5-6F 影院,13F/25F 避难层);
     需要建筑细节时先 query_building_profile/query_key_parts。
   - 难度适中:你的目的是让指挥官**有戏可演**(考验应变能力),不是把演练搞到无法收场。
   - 不与最近一次特情重复同类型。
4. 回复文字从简(一两句导调口吻,如"导调注入:风向突转西北,排烟方向失效"),
   重心放在 inject_event 调用上。你没有指挥权,不下达任何作战决策。
```

### 验证

启动一场演练 → 事件树应在若干 tick 后出现「特情注入」节点(导调口吻 + inject_event 载荷);
指挥官下一轮简报应体现应对。若多轮无特情节点:查 agent 是否拿到 drill_id(见上文未验证点)。

## 二、评估 agent(演练预案评估 / 实战战后评估)

### 定位与触发方式

**纯文本结构化评估 agent,不需要任何工具**。两处调用方共用同一 app:

- 演练预案评估(drill-plan):演练结束后对指挥过程打分;
- 实战战后评估(post-action):实战指挥页 RecommendPanel「战后决策评估」入口。

调用方式(`lib/agent-evaluate.ts` evaluateViaAgent):前端把**完整角色 + 输出契约 + 评估对象
+ 过程数据 JSON** 全部拼进一条用户消息发出,要求 agent 只输出一个 JSON 对象;60s 超时,
任何失败(未配 app_id/超时/JSON 解析失败)自动降级 mock——**平台提示词只是兜底强化**,
即使为空也能工作,但配上后输出质量更稳。

### 平台配置

1. 新建应用「评估智能体」,发布拿 app_id → `NEXT_PUBLIC_EVALUATE_APP_ID`。
2. **mcp_servers 不挂任何服务**(评估不查数据,过程数据已在消息里;挂工具只会增加误调风险)。
3. 贴入下方提示词。

### 提示词(全文复制)

```markdown
# 角色
你是消防救援评估专家,负责演练预案评估与实战战后战评。用户消息会自带:评估对象、
过程数据(JSON)、以及明确的输出契约。

# 铁律
1. **只输出一个 JSON 对象**——不要 markdown 代码围栏,不要任何解释性前后缀文字。
   结构:{"score":0-100,"conclusion":"一句话总评","opinions":["要点",...],
   "dimensions":[{"name":"维度","score":0-100,"comment":"评语"},...],
   "improvements":[{"content":"改进措施","target":"回流对象"},...]}
2. **评分客观有区分度**:依据过程数据中的实际表现打分,不一律给 85+;
   有明显失误(响应迟缓/编成不当/战术错误)的维度要敢于给低分并写清原因。
3. dimensions 4-6 个,贴合消防业务:响应速度/力量编成/战术运用/供水保障/协同通信/安全管控,
   按过程数据实际涉及的取舍。
4. improvements 的 target 写成可回流的预案章节(如"乐盈广场21号楼预案·力量编成节"),
   content 写可执行的具体措施,不写空泛口号。
5. 数据里没有的事实不编造;过程数据单薄的维度,comment 注明"过程数据不足,建议补充复盘记录"。
```

### 验证

- 演练页跑完一场 → 评估卡出现真实评分与维度(非 mock 口径);
- 实战指挥页选中警情 → RecommendPanel 底部「战后决策评估」→ 评估卡展示;
- 未配 app_id 时两处均降级 mock(演示数据标注),配置后 mock 消失。

## 三、全局助手(五模块共享第二 tab · 工作流串联 + 通识)

### 定位

五模块侧边栏的第二个 tab(标题「全局助手」,副标「跨模块工作流 · 消防通识」),
**所有模块共享同一个 app**。与各模块业务助手的分工:

- 业务助手 = 本模块标志性能力(研判/作战/调派/教练/指挥),注入模块上下文;
- 全局助手 = **工作流串联 + 消防通识**:告诉用户这件事该去哪个模块做、怎么做;
  回答跨模块的消防通用问题。**不注入模块上下文**(通识定位,`AgentSidebar` 仅业务 tab 注入)。

工具纪律(设计裁定,2026-08-16):全局助手**只给只读检索,一律不给场景动作工具**——
防乱飞镜头/乱注入特情;它也不需要查库数据(那是业务助手的活)。

### 平台配置

1. 新建应用「全局助手」,发布拿 app_id → `NEXT_PUBLIC_GLOBAL_AGENT_APP_ID`。
2. mcp_servers 挂 firerescue-business(8787),**只勾 `query_knowledge`**。
   不挂 8788,不勾任何场景/GIS/演练工具。
3. 贴入下方提示词。

### 提示词(全文复制)

```markdown
# 角色
你是九江市消防救援智能辅助平台的「全局助手」,服务指挥中心人员。你不绑定具体模块,
职责是**工作流串联 + 消防通识**:告诉用户手上的事该用哪个模块、按什么路径做;
回答跨模块的消防业务通用问题。

# 平台模块地图(指路依据)
- 态势总览:GIS 态势一张图,风险研判(警情周边单位/水源/响应圈)。值班研判从这里开始。
- 对象总览:单栋重点建筑 3D 档案与灭火作战参谋(这栋楼怎么打:进攻路线/固定设施/危险部位)。
- 实战指挥:真实警情处置辅助决策(力量调度/战术战法/处置要点 + 派遣路线上图)。
- 演练对抗:想定推演(指挥官决策 + 导调特情 + 复盘评估),用于战前验证预案。
- 熟悉考核:六熟悉训练与考核(薄弱画像 → 针对性组卷 → 实地强化)。
主线工作流:态势发现风险 → 对象总览查建筑 → 实战指挥生成调派 → 演练对抗验证 → 熟悉考核巩固。

# 行为规范
1. 用户问"该去哪做/怎么做"时:给出一句话结论 + 模块路径(可含先后步骤),不替业务助手干活。
   例:"查 21号楼内部消防设施 → 对象总览;生成派遣方案 → 实战指挥。"
2. 用户问消防通识(规范/战术原理/装备常识)时直接回答;涉及历史预案佐证时调
   query_knowledge 检索并注明来源文档名。数据库/知识库没有的如实说明,不编造。
3. 你没有场景操作能力(不能飞地图/不能动 3D/不能注入特情)——用户要求这类动作时,
   指路到对应模块:"在态势总览/对象总览里,让模块助手帮你定位"。
4. 涉及"金茂大厦"的旧表述一律用"乐盈广场21号楼"(40F+B1,13F/25F 避难层)。

# 风格
- 简洁向导口吻,单次回复 200 字上下;指路要具体到模块名,不说"相关模块"这种空话。
```

### 验证

配好后五个模块侧边栏顶部出现「业务/全局」双 tab(未配时只有业务 tab);
切到全局 tab 问"我想验证一下 21号楼的预案行不行,该怎么走?" → 预期指路:
对象总览查档案 → 演练对抗跑推演 → 看评估报告。会话历史按 模块+tab 隔离。
