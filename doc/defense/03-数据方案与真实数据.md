# 03 · 数据方案与真实数据

> 回答"数据是真的吗、从哪来、怎么保证 agent 不编造"。

## 1. 数据权威三权分立（核心设计）

**原则：数据库回答"档案和业务事实"，uStudio 回答"场景里实际建了什么"，DrillSession 回答"本局演练发生了什么"。三者不能互相冒充。**

| 业务问题 | 权威来源 | 工具 | 可信度规则 |
|---|---|---|---|
| 建筑档案/重点部位/设施台账 | znya PostgreSQL（key_buildings/key_floors/fire_facilities） | `query_building_profile` 等 | 台账事实 ≠ 3D 建模 ≠ 实时传感 |
| 场景实际建模 | uStudio 场景树 | `list_floors`/`query_scene_facilities` | 浏览器离线不得伪造 |
| 台账 vs 模型一致性 | znya + uStudio 对账 | `reconcile_building_facilities` | 返回 matched/ledger_only/scene_only/count_mismatch |
| 当前可用力量 | `fire_force_items.status` | `query_force_availability` | **禁止用站点编制数冒充实时可用数**；默认排除演示数据 |
| 正式预案 | `emergency_plans` + 9 类结构化子表 | `query_operational_plan` | published_only 拒草稿 |
| 派遣路线/ETA | AMap + znya 点位 | `plan_dispatch` | 路径是规划结果，是否可派由力量可用性决定 |
| 演练过程 | DrillSession | `query_scene_state` | `online:true` 才是实时；`persisted:true` 明确非实时 |

**统一 ID 图**：`incident_id → building_id → scene_id → uStudio 对象 id`，`building_id → plan_id / key_floors / fire_facilities`。`resolve_operational_context` 统一解析，**agent 禁止从名称猜 UUID**——跨源关联全部走显式 ID 图，这是"agent 不张冠李戴"的结构性保证。

## 2. 真实数据清单（演示主对象：乐盈广场 21 号楼）

| 数据 | 真实性 |
|---|---|
| 建筑 3D 场景包 | 赛事平台真实场景（40F+B1，69k mesh；13F/25F 避难层） |
| 建筑档案/重点部位/设施台账 | znya 生产库真实录入（联系到楼层粒度） |
| 消防站/车辆/人员明细 | `fire_stations` + `fire_force_items`（按状态区分在位/出警/维保） |
| 水源/重点单位/警情 | znya 生产库（GCJ02 坐标） |
| 正式预案 | znya `emergency_plans` 已发布版本 + 结构化子表 |
| 历史预案知识库 | 平台原生知识库挂载（自建 embedding 链路已裁撤） |

**数据口径治理实例（可讲的真实故事）**：预案文本与档案曾存在"建筑高度 258m vs 150m"冲突——我们做了三条 alembic 迁移把 **znya 侧全部清洗为档案口径 150m**（plan_safety_tips 55 行 / plan_basic_info / key_buildings 主表），并让 agent 如实声明来源；唯一残留是平台知识库里的旧预案原文，演示时如实说明而非掩盖。这个案例本身展示了对数据口径的治理能力。

## 3. 诚实性设计（贯穿全链路）

1. **`{data, meta}` 信封**：聚合工具统一返回 `source/updated_at/completeness/is_demo/truncated/warnings`；提示词强制"先查 meta 再下结论"，不完整/演示/非实时数据必须显式标注。
2. **证据 chips**：Commander 每轮调整携带 1–3 条依据（kind=plan/archive/force/water/knowledge/warning 六类），评委可点开核对；数据缺失时必须出 `warning` 类证据（如"力量明细缺失，按预案基准配置"）。
3. **对账工具**：`reconcile_building_facilities` 公开台账与 3D 建模的差异（如"台账 5 层为 0，以场景 111 件为准"）——不一致本身就是有价值的输出。
4. **已知缺口如实申报**：`fire_facilities` 无 `scene_object_id`，当前只能按"类型+数量"对账，逐设备绑定列为数据治理项；知识库旧口径文本残留——都写在蓝图 §7 待治理清单里。

## 4. 演练数据所有权

- 浏览器 confront-store 是实时真源；DrillSession 是服务端快照（每局唯一 drillId，LRU 500 局，文件持久化重启可读）。
- 评估结论 + 改进措施回流预案库（znya 建档），形成"演练 → 评估 → 修订预案"的业务闭环。
- 归档进 PostgreSQL 审计层为既定演进方向（并发/审计需求触发时）。
